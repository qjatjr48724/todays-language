## 1. 코드를 작성하기 전에 생각하기
### 멋대로 추측하지 않는다. 헷갈리는 점을 숨기지 않는다. 장단점을 명확이 드러내라.

실행하기 전에:
  - 가정한 내용을 명확하게 밝히고, 확실하지 않으면 반드시 질문한다.
  - 요청을 여러 가지 방법으로 해결이 가능하다면, 맘대로 선택하지 말고 각 방법을 장단점과 함께 제시한다.
  - 더 간단한 방법이 있다면 언급한다. 필요하다면 반박한다.
  - 이해가 되지 않는 부분이 있다면 당장 멈추고 무엇이 헷갈리는지 말하고 질문한다.

## 2. 단순함이 최우선
### 문제를 해결하는 데 필요한 최소한의 코드만 작성한다. 추측성 코드는 일절 포함하지 않는다.
- 변경된 모든 코드가 사용자의 요청에 직접 연결되는지 확인하고, 연결되지 않으면 손대지 않는다.
- 일회용 코드에는 추상화가 필요없다.
- 요청하지 않은 "유연성"이나 "설정 가능성"은 없다.
- 불가능한 시나리오에 대한 오류 처리가 없다.
- 200줄을 작성했는데 50줄로 줄일 수 있다면 다시 작성한다.

스스로에게 "선임 개발자가 이것이 지나치게 복잡하다고 말할까?"라고 질문한다. 만약 그렇다면 단순화하라.


## 3. 필요한 부분만 변화시킨다.
### 꼭 필요한 것만 수정한다. 자신이 저지른 일은 스스로 수습한다.

기존 코드를 편집할 때:
  - 인접한 코드, 주석 또는 서식을 멋대로 "개선"하지 않는다.
  - 멀쩡한 것을 굳이 리팩토링(Refactoring)하지 않는다.
  - 기존 스타일과 일치시킨다. 비록 너가 다르게 표현하더라도.
  - 관련이 없고 사용되지 않는 코드를 발견하면 바로 삭제하지 말고 언급한다.
    - ex) "~에 대한 ABC 파일이 지금은 사용되지 않는 것 같습니다. 정리할까요?"
    - ex) "get_user 함수에 안 쓰이는 import가 있는데 정리할까요?"

변경 사항으로 인해 사용되지 않는 파일이 만들어지는 경우:
  - 사용자가 변경한 내용으로 인해 더 이상 사용되지 않는 import/함수/변수를 제거한다.
  - 요청받지 않는 한 기존의 사용되지 않는 코드를 삭제하지 않는다.

테스트: 변경된 모든 코드는 사용자의 요청과 직접적으로 연경되어야 한다.


## 4. 목표를 기반으로 실행하라.
### 성공 기준을 정의하고, 기준이 충족될 때까지 반복한다.

문제를 검증 가능한 목표로 전환한다:
Step 1) 성공 케이스와 실패 케이스 각각의 테스트를 작성한다.
    -> 검증: 현재 코드가 실패하는지 확인한다.

Step 2) 코드 수정
    -> 검증: 실패 케이스로 작성한 테스트가 통과하는지 확인한다.

Step 3) 회귀 확인
    -> 검증 : 수정 전 코드의 기존 테스트도 전부 통과하는지 확인한다.
